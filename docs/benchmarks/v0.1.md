# auspex v0.1 request-path benchmarks

**What this measures:** the latency and heap allocations auspex adds to a single
HTTP request, against the v0.1 targets:

> **< 50 µs p99 added latency, < 2 request-path allocations** (enabled,
> root-span-only).

Reproduce with `cargo bench --bench hotpath` (see `benches/hotpath.rs`).

## Method

The request path is runtime-independent — `TracerService::call` builds the root
span and the `ResponseFuture` finalizes it and `try_send`s it to the export
channel; only the *background export worker* needs a Tokio runtime, and it is
deliberately off the request path. So the bench drives the full request
synchronously with a no-op waker, which isolates request-path cost from the
worker/export thread entirely.

- **Latency** is reported as **added** latency: `auspex_path − bare_baseline` at
  each percentile (200k samples each, after 20k warmup). Baseline subtraction
  cancels the per-iteration `Instant` overhead, which matters at this sub-µs
  scale.
- **Allocations** are counted with a process-global counting `GlobalAlloc`,
  snapshotted around a single warmed call (request construction excluded, since
  it is identical for baseline and auspex). Reported as the steady-state
  minimum over 5k samples (deterministic across runs).

## Results

Measured on the conditions in the footnote. Latency reproduces within ~10%
across three runs; allocation counts are exact.

| Scenario | p50 added | p95 added | p99 added | allocs/req | targets |
|---|---|---|---|---|---|
| Disabled middleware | ~0 µs | ~0 µs | ~0 µs | **0** | ✅ both |
| **Enabled, root-span-only** | 1.9 µs | 2.2 µs | **2.7 µs** | **3** | ✅ latency · ⚠️ allocs |
| Enabled, root + 3 child spans | 5.0 µs | 5.5 µs | 7.1 µs | 9 | ✅ latency |

Baseline (bare service): p50 ≈ 42 ns, 0 allocations.

## Verdict

- **Latency target: met with a wide margin.** The enabled root-span path adds
  **~2.7 µs at p99** — about 18× under the 50 µs budget. Even a root span plus
  three child spans stays ~7 µs. Disabled mode is free (the middleware takes a
  no-span fast path: 0 added latency, 0 allocations).

- **Allocation target (< 2): not met as stated; 3 for a full HTTP root span.**
  After interning fixed-vocabulary values (commit `0769766`), the count dropped
  from 10 to 3. The remaining three are *all genuinely dynamic strings*:
  `url.path`, `user_agent.original`, and `server.address`. Each varies per
  request and must outlive the request (it travels through the async export
  channel to the worker), so each is an irreducible owned allocation. The
  `Box<OtelSpan>` per-span state is amortized by `tracing-subscriber`'s span-slot
  reuse and does **not** appear in the per-request count.

### Why < 2 is the wrong number (and what the right one is)

The hard floor is **one allocation per captured dynamic string attribute**. You
cannot "allocate once" for these: the content differs every request and is handed
off to another thread, so a reused buffer can't work without a per-request
arena returned after export (a large design change not justified for v0.1).

What we *can* (and did) drive to zero is the fixed-vocabulary values — HTTP
method, URL scheme, protocol name, and the no-route span name — via
`field::intern_wellknown` (`Cow::Borrowed(&'static str)`).

So the realistic decomposition for the default HTTP root span is:

- method / scheme / protocol / span-name (no route): **0** (interned)
- `url.path`: **1** (always captured, always dynamic)
- `user_agent.original`, `server.address`: **1 each** (captured when the header
  is present)

A span that captured *only* method + path would hit **1** allocation and meet
`< 2`. The default also captures `user-agent` and `host` (both standard OTEL
attributes), which is where 2 of the 3 come from.

**Recommendation:** restate the target as **"≤ 1 allocation of fixed overhead +
1 per captured dynamic string attribute"** (so 1 for a minimal span, 3 for the
default HTTP span). If a strict `< 2` is desired by default, make
`user_agent.original` / `server.address` capture opt-in — that is a product
decision about default attribute richness, not a perf limitation. Either way,
the latency budget is met comfortably and the allocation cost is now minimal and
fully accounted for.

## Comparison vs the OpenTelemetry stack

Is 3–5 allocations/span good? Reference point: the same span workload measured
under `opentelemetry_sdk` + `tracing-opentelemetry` (the mainstream stack), same
counting allocator, both with serialization disabled (auspex enqueues to its
channel; the OTEL side uses a no-op `SpanProcessor`). See `benches/compare_otel.rs`,
run with `just compare-otel` (it is feature-gated behind `compare-otel` so the
OTEL dependency tree is never compiled in a normal build/test/CI run).

| Stack | allocations/span (create + close, 6 attributes) |
|---|---|
| **auspex** | **5** |
| `opentelemetry_sdk` + `tracing-opentelemetry` | **19** |

**auspex does ~3.8× fewer allocations per span than the mainstream stack** — and
that is before the OTEL stack serializes anything. The v0.1 `< 2`
absolute was aspirational; the meaningful, defensible claim is "multiples leaner
than the OpenTelemetry SDK." The remaining auspex allocations are all genuine
per-request client data (see above), and the fixed-overhead/server-identity
fields are interned to zero.

*Caveat:* the latency column of that bench is **not** a fair head-to-head — the
OTEL side's no-op processor drops spans on end, while auspex finalizes and
enqueues every span; a real `BatchSpanProcessor` does comparable buffering work.
Use the request-path latency above (~2.7 µs p99 added) as auspex's figure. The
allocation comparison is fair (both build the full in-memory span; neither
serializes).

The `opentelemetry*` crates are **dev-dependencies only**, pulled in solely for
this comparison — they never enter the shipped crate (the whole point of auspex).

## Notes / limitations

- The request-path bench (`hotpath`) is vs a bare service with no tracing; the
  allocation comparison vs `tracing-opentelemetry` is the separate `compare_otel`
  bench (above).
- `cargo bench` is not gated in CI (numbers are machine-dependent); the bench is
  compile-checked via `cargo clippy --all-targets`.
